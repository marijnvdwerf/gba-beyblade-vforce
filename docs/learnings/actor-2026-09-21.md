# actor.c — 2026-09-21

## sub_8058068 (0x8058068) — matched

Summed frame costs of one `ActorSequenceEntry`. Everything in the parked draft
was semantically right; the whole residue was one instruction pair:

```
target   mov r4, r5 / ldrh r1, [r4, #8] / add r4, #2
draft    mov r4, r5 / add r4, #8 / ldrh r1, [r4, #0] / add r4, #2
```

i.e. where the `+8` (the `frames` member offset) lives: in the load's
displacement, or folded into the induction variable's initial value.

### What made it match

`entry->frames[index]` -> `*(entry->frames + index)`. Nothing else changed:
same locals, same `for`, same types.

### Why (agbcc 2.8 expander, from `--all-passes` dumps)

`expand_expr`'s `ARRAY_REF` case, when the index is not an `INTEGER_CST`,
rewrites `a[i]` into `*(&a[0] + i)` and expands *that*. `&entry->frames[0]`
is a unit, so the constant is added first. Pre-loop RTL of the draft:

```
reg34 = index << 1
reg35 = entry + 8        <- loop-invariant, hoisted ("Insn 60 ... moved to 104")
reg36 = reg35 + reg34
reg37 = zext(mem:HI[reg36])
```

`.loop` then reduces the address giv with `add (plus entry 8)`, so the giv's
initial value costs the extra `add r4, #8`.

Writing the pointer arithmetic in the source instead sends it through the
front end's `fold`, which reassociates `(entry + 8) + index*2` into
`(entry + index*2) + 8`; `INDIRECT_REF` expands its address with
`EXPAND_SUM`, and Thumb's `memory_address` keeps a `reg + const` HImode
displacement. Pre-loop RTL becomes:

```
reg35 = entry + index*2
mem:HI[reg35 + 8]
```

giv `add_val = entry` -> initial value `mov r4, r5`, `+8` stays in the load.

### Layout: `ActorSequenceEntry` is not mis-modelled

The `+8` displacement with a stride of 2 also falls out of a
`COMPONENT_REF`-on-top chain (`entry->frames[index].field`): `expand_expr`
for `COMPONENT_REF` uses `get_inner_reference`, which accumulates the
variable part as `offset` (added to the base) and the constant part as
`bitpos` (kept as a displacement). Probed and it produced exactly the target
shape — but with a stride of 4, because agbcc has
`STRUCTURE_SIZE_BOUNDARY = 32`:

* `struct { unk16 unk0; }` element -> `add r4, #4`
* `struct { unk8 unk0; unk8 unk1; }` element -> `add r4, #4`

So no 2-byte struct exists in this compiler and the element cannot be an
aggregate; `unk16 frames[]` at offset 8 is correct and the header is
unchanged. `unk16 frames[1][1]` with `frames[index][0]` was also probed: the
inner variable-index `ARRAY_REF` still takes the `*(&a[0] + i)` rewrite, so
it regresses to the hoisted `add r4, #8`.

### Signedness / widths

`ldrh [r5,#4]` for the count and `ldrh [r4,#8]` for the frame: unsigned
loads, no sign extension anywhere, `blo`/`bhs` on the loop test -> `unk32`
counter against `unk16 unk4` is right. `total` lives in `r8` and returns
through `mov r0, r8`; the `lsl #16 / lsr #16` on entry is the `unk16 sequence`
parameter being passed on to `sub_8058038`.

### Folds

`total`, `index` and `entry` are all the minimum set: removing `entry`
(calling `sub_8058038` inside the condition) is not expressible, and no temp
was added. The zero in `r8` doubles as the loop-entry comparison operand
(`cmp r8, r0` before the first iteration) — that is agbcc CSE'ing
`total == 0` with `index == 0`, not a source-level alias.

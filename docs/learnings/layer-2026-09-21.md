# layer.c — 2026-09-21

## sub_8059904 (0x8059904) — MATCHED

Two-line forwarder to `sub_80596AC`. The target materialises each constant with
`mov rX, #0xB0` + `lsl rX, #7` / `#6` (i.e. 0x5800 and 0x2C00), and computes
`layer->field_C + 0x5800` into its own register before the subtraction.

### Why the obvious shapes fail

agbcc's `fold`/`associate` **always** reassociates `A - (B + K)` with `K` an
integer constant into `(A - K) - B`. Once `K` is negated it no longer fits
`imm8 << n`, so it comes out of the literal pool:

| source shape | result |
| --- | --- |
| `A - layer->field_C - 0x5800` | `ldr r?, [pc]` = 0xFFFFA800, add, then `sub field_C` |
| `A - (layer->field_C + 0x5800)` | same (associate fired) |
| `A - (0x5800 + layer->field_C)` | same |
| `x -= layer->field_C + 0x5800;` (compound assign) | same |

Also true when `A` is already a local (so it is not "both operands must be
sums" — associate fires on the constant alone).

The only way to keep `+0x5800` as a real PLUS in the tree is to give it its own
variable. `mov #0xB0; lsl #7` is then just agbcc's ordinary synthesis of a
positive `imm8 << n` constant — no literal-valued temp needed.

### Ordering

The target interleaves per-argument: numerator1, centre1, sub1, numerator2,
centre2, sub2. agbcc emits statements in source order, so the centre locals
must be assigned *between* the two numerators, and the subtraction must be its
own statement (putting both subtractions in the call's argument list sinks them
both to the end — measured, v3 in the probe matrix).

Matching form (4 locals, all byte-required):

```
x = entry->y + (entry->unkC << 7);
centerX = layer->field_C + 0x5800;
x -= centerX;
y = entry->unk8 + (entry->unkC << 7);
centerY = layer->field_10 + 0x2C00;
y -= centerY;
sub_80596AC(layer, x, y);
```

Fold results: removing `x`/`y` is impossible (the centre must be computed after
the numerator). Reusing a single `center` scratch for both axes costs an extra
register (`push {r4,r5,r6}` and an extra `adds r5, ...`) — distinct
`centerX`/`centerY` locals are what matches.

Signedness: `field_C`/`field_10` are `s32` (existing header); `MotionEntry`
`y`/`unk8`/`unkC` stay `unk32`. No sign-sensitive instruction in this function,
so nothing was re-signed.

## sub_8059DDC (0x8059DDC) — MATCHED

Tile-map rectangle fill. Parked draft had the right semantics and the right
instruction *sequence* from the start; the whole residue was register roles
plus one extra copy in the target.

### Two independent levers, both needed

1. **A separate `currentRow` loop variable** instead of stepping the `row`
   parameter. With `for (; row < rowEnd; row++)` agbcc gives `row` a fresh
   pseudo that lands in r4 and pushes `address` down into r2 — the whole
   allocation is then permuted against the target. With
   `for (currentRow = row; ...; currentRow++)` the `row` parameter coalesces
   with its incoming r2 and `address` takes r3, exactly as in the target.
   (Declaration-order permutations of the locals changed nothing — measured
   three orders, byte-identical output.)

2. **The bounds written inline in the loop conditions**, not precomputed into
   `rowEnd` / `columnEnd` locals. The target has an extra `mov r5, r1` at
   0x48, i.e. the loop bound lives in a *second* pseudo copied from the one the
   entry guard compared against. That is what `currentRow < row + height`
   produces: agbcc duplicates the condition for the entry guard
   (`add r1, r2, r4; cmp r2, r1`), then loop-invariant motion hoists
   `row + height` into the preheader, where CSE turns the recomputation into a
   copy of r1. A precomputed `rowEnd` local emits `add r5, r2, r4` once and is
   two bytes short.

   Same for the inner loop: `currentColumn < column + width` is hoisted to the
   top of the *outer* loop body (`mov r1, r10; add r0, r1, r6`), which is where
   the target computes it — one level only, not out to the function preheader.

Final form (4 locals, no `rowEnd`/`columnEnd`):

```
for (currentRow = row; currentRow < row + height; currentRow++) {
    for (currentColumn = column; currentColumn < column + width; currentColumn++) {
        *address = data & 0x3FF;
        address++;
    }
    address += rowStride;
}
```

Widths: `rowStride` must be `unk16` — the target truncates with
`lsl #16 / lsr #16` after `(1 << field_5F) - width`. `data & 0x3FF` is written
inside the inner loop; agbcc hoists both the 0x3FF literal (into r8, function
preheader) and the `and` (into the outer loop body) by itself.

## sub_8059F20 (0x8059F20) — MATCHED

Bounded string render, sibling of the already-matched `sub_8059EBC`.

### Signedness

`bgt` / `ble` for `index <= end` prove a **signed** comparison, so `index` must
be `s32`, not `unk32` (the parked draft had `unk32 index` with `s32 end` — the
usual arithmetic conversions would have made the compare unsigned, i.e. the
draft was semantically wrong, not just badly allocated). `start` / `length`
stay `unk16` (`lsl #16 / lsr #16`, not `asr`).

### The r4/r5 residue: duplicated `currentColumn++`

With that fixed the instruction stream was already identical, with `index` and
`currentColumn` swapped between r4 and r5. Neither declaration order,
assignment order, nor splitting `string[index++]` moved it (three probes,
byte-identical output each time) — as expected, since none of them changes the
insn stream and therefore none changes `REG_N_REFS` / `reg_live_length`.

What decides it is agbcc's global-alloc priority
`floor_log2(n_refs) * n_refs / live_length`, with `n_refs` weighted by loop
depth. Measured from the `.lreg` dump of the draft:

| pseudo | n_refs | live_length | priority |
| --- | --- | --- | --- |
| `index` (36) | 13 | 38 | 3·13/38 = 1.026 |
| `currentColumn` (37) | 9 | 35 | 3·9/35 = 0.771 |

Higher priority is allocated first and takes r4. The target gives r4 to
`currentColumn`, so the original must reference `currentColumn` more often —
four more weighted refs, i.e. two more in-loop refs.

That is an `else if` chain with the increment written out in **both** arms:

```
if (character == '\n') { row += 2; currentColumn = column; }
else if (character == ' ') { currentColumn++; }
else { sub_8059E5C(...); currentColumn++; }
```

n_refs for `currentColumn` becomes 13 (1 + 6·2) → priority 3·13/35 = 1.114,
above `index`, and the allocation flips to match. The two increments are then
merged again by cross-jumping (`jump2` runs after reload), so the final code
has a single `add r4, #1` at 0x5A reached by both the `beq` from the space test
and by fallthrough — exactly the target. Register allocation therefore sees a
source shape that the emitted code no longer shows.

Note the already-matched `sub_8059EBC` directly above uses the single-increment
shape; it is not sensitive to this, so the two functions legitimately differ.

## sub_8059404 (0x8059404) — MATCHED

DMA row copy into a 16-bit tile map, sibling of `sub_80594FC` (byte map).

### The `(E * 2) / 2` rule (the whole function turns on this)

`DmaCopy(..., Size, 16)` expands to `DMA_ENABLE | ((Size) / (16 / 8))`. The
target emits `lsl #1` / `lsr #1` pairs for all three transfer sizes. Measured
in a scratch TU (`probe_a` … `probe_g`):

| source | emitted |
| --- | --- |
| `DmaCopy(3, p, q, x * 2, 16)` | `orr x, #0x80000000` — the front-end folds `(x*2)/2` |
| `DmaCopy(3, p, q, (x - y) * 2, 16)` | same, folded |
| `bytes = x * 2; DmaCopy(3, p, q, bytes, 16);` | `lsl bytes,#1` … `lsr bytes,#1`, **not** folded |

So the fold is a front-end `fold()` on the whole expression; routing the byte
count through a variable (or an assignment-expression, the idiom already used
in `sub_80594FC`) defeats it. That is why the target has three distinct size
variables — and why they are then loop-invariant sets that LICM can hoist into
the preheader (a single `size` variable reused for all three is set 3× in the
loop and is therefore **not** hoistable; measured, 20 extra in-loop bytes).

The first size doubles as the source-pointer offset (`source + firstSize`), so
its `lsl` has two uses and the value lands in r9.

### Statement order and the assignment-in-argument idiom

`DmaSet` stores Srcp, Destp, then the control word, so an argument-position
assignment `(firstSize = …)` is evaluated **after** the destination
expression. That is what puts `srcX * 2` ahead of `horizontalStride - srcX` in
the hoisted preheader. Writing `firstWidth = horizontalStride - srcX;` as a
statement before the `DmaCopy` reverses those two and diverges at 0x5E.

### The head

`source += offset * 2;` must sit after the mask/stride block while
`y * columnCount + x` is computed before it — i.e. the map offset is its own
local, and `layer->columnCount` is read in that expression with `columns`
cached on the following line:

```
offset = y * layer->columnCount + x;
columns = layer->columnCount;
```

CSE collapses the two field reads to one `ldr`, and the spill of `columns` to
sp+4 then lands after the `mul`, as in the target. Caching `columns` first and
writing `offset = y * columns + x` puts the spill before the `mul` and permutes
the rest (33 normalized lines off; this form: 0).

### Pointer widths

`source` and `screen` are `unk8*` with explicit `* 2` on every index
(`screen + rowOffset * 2 + srcX * 2`, `source += columns * 2`). `unk16*` with
implicit scaling produced identical code for the pointers but does not give the
shared `firstWidth * 2` that the size variable needs.

`layer->field_5F` is re-read inside the loop (the volatile DMA stores block the
hoist), while `horizontalStride`, `rowMask`, `screen` and `columns` are spilled
to sp+0xC/8/0/4 and reloaded — that is the allocator, not the source.

   in the declaration list); there is no first divergence. The final source

2. Folding `offset` into `source += (y * layer->columnCount + x) * 2;`

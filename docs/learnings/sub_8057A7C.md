# `sub_8057A7C` matching notes

Status: left as `INCLUDE_ASM` in `src/system.c`; no exact C match was reached. The dump was not deleted.

## Best source reached

The best source-shaped/m2c-derived body retained during the search was the following. It is semantically an RGB555 palette brightness adjustment over eight entries. It is included here because it was the closest useful starting point, not because it matches the ROM.

```c
void sub_8057A7C(u16* src, u8 paletteIndex, s32 offsetInput)
{
    volatile u16* var_r6;
    s16 temp_r5;
    u16* var_r7;
    u16 temp_r0;
    u16 temp_r2;
    u16 temp_r2_2;
    u16 var_ip;
    u16 var_r1;
    u16 var_r3;
    u16 var_r4;

    var_r7 = src;
    var_r6 = (volatile u16*)(((u32)(paletteIndex << 0x18) >> 0xF) + BG_PLTT);
    var_ip = 0;
    temp_r5 = offsetInput;
    do {
        temp_r2 = *var_r7;
        temp_r2_2 = (temp_r2 & 0x1F) + temp_r5;
        var_r3 = ((u32)(temp_r2 & 0x3E0) >> 5) + temp_r5;
        var_r4 = ((u32)(temp_r2 & 0x7C00) >> 0xA) + temp_r5;
        var_r1 = temp_r2_2;
        if ((s32)(s16)temp_r2_2 > 0x1F) {
            var_r1 = 0x1F;
        }
        if ((s32)(s16)var_r3 > 0x1F) {
            var_r3 = 0x1F;
        }
        if ((s32)(s16)var_r4 > 0x1F) {
            var_r4 = 0x1F;
        }
        if ((((s32)(s16)var_r1) << 0x10) < 0) {
            var_r1 = 0;
        }
        if ((((s32)(s16)var_r3) << 0x10) < 0) {
            var_r3 = 0;
        }
        if ((((s32)(s16)var_r4) << 0x10) < 0) {
            var_r4 = 0;
        }
        *var_r6 = (s16)var_r1
            + ((s32)(var_r3 << 0x10) >> 0xB)
            + ((s32)(var_r4 << 0x10) >> 6);
        var_r7 += 1;
        var_r6 += 1;
        temp_r0 = var_ip + 1;
        var_ip = temp_r0;
    } while ((u32)temp_r0 <= 7U);
}
```

This body is deliberately recorded with its mechanical narrowing/cast expressions. The later natural variants were preferable as C, but the body above preserved more of the target's narrow-value operations and register pressure.

Inference: `r1` is narrowed to eight bits and scaled by 512, so the second argument is naturally a `u8` palette bank/index. The target's `r2` normalization proves that the third incoming value is narrowed to a signed halfword in the function, but does not by itself prove that the ABI-level parameter is declared `s16`; a wider parameter followed by a signed-halfword local can produce this sequence.

The loop choreography is also significant. The target loads the source color into `r2`, keeps the green and blue masks in callee-saved `r9` and `r8`, and leaves the channel values in `r1` (red), `r3` (green), and `r4` (blue) before clamping/packing:

This is not merely the semantic order red/green/blue. It indicates that the source expression tree and local live ranges caused the compiler to retain the loaded color in `r2`, use `r0` as the green intermediate, use `r1` as the blue intermediate, and then materialize the final channel values in `r1/r3/r4`.

## First divergence by variant

The following records the major variants, rather than every declaration-order or one-line permutation. Repeated permutations in the same group had the same first mismatch unless noted.

### 1. Initial m2c-shaped body

Source shape: `u8 paletteIndex`, `s16 temp_r5`, explicit `var_r1/var_r3/var_r4` channel temporaries, explicit narrow casts, and the shifted-address expression shown in the best-source listing.

First mismatch:

```text
target 0x00000018: mov r1, #248
current 0x00000018: <no instruction>
```

The current object reached the address calculation and loop-counter setup, but did not materialize the target's green-mask setup at that point. The mask constants were materialized later/differently, so the first visible mismatch was an insertion at `0x18`; subsequent differences were mostly register allocation and scheduling consequences.

### 2. Same m2c body with explicit mask locals

Source shape: added `u16 maskGreen = 0x3E0` and `u16 maskBlue = 0x7C00`, with the loop using those locals.

First mismatch:

```text
target 0x00000020: asr r5, r2, #16
current 0x00000020: lsr r5, r2, #16
```

The target needs a signed halfword extraction. In this variant, the value reaching the `s16` temporary was treated as a logical narrow value by the compiler, so the extraction became `lsl #16` followed by `lsr #16` rather than `lsl #16` followed by `asr #16`. Inference: the assignment/cast path did not preserve the signedness needed for the extension; merely declaring the destination temporary `s16` was insufficient in this expression arrangement.

### 3. Wide-local offset experiment

Source shape: `s32 temp_r5; temp_r5 = (s16)offsetInput;`, retaining the explicit mask locals.

This corrected the offset-extension opcode. The first remaining mismatch was:

```text
target 0x00000022: mov r4, #248
current 0x00000022: mov r3, #248
```

Thus the wide local changed the `0x20` `lsr` into the target `asr`, but it did not force the target's blue mask into `r4`/`r8` setup. The mask setup and the later channel registers remained allocated differently.

### 4. Natural prototype with direct `s16 offset`

Source shape: the reviewed natural prototype/body:

```c
void sub_8057A7C(u16* src, u8 bank, s16 offset)
```

with `s16 red`, `s16 green`, `s16 blue`, plain channel expressions, plain `> 31` and `< 0` clamps, and `BG_PLTT + (bank << 9)`.

First mismatch:

```text
target 0x0000000c: lsr r1, #15
current 0x0000000c: <no instruction>
```

The direct `u8` bank form did produce the expected bank scaling in the successful portions, but a direct `s16` parameter caused the compiler to treat the offset as already narrowed. Consequently it omitted the target's incoming-value normalization sequence in the tested body. This is why a natural ABI prototype of `s16 offset` was semantically plausible but did not reproduce the entry code.

### 5. Natural body with a wide offset local

Source shape: `u8 bank, s16 offset` in the prototype, plus `s32 offsetValue = offset`, with the natural channel and clamp code.

The wide local restored the need for a signed extension in some tested builds, but the first remaining mismatch moved to the invariant mask setup:

```text
target 0x00000018: mov r1, #248
current 0x00000018: <no instruction>
```

The entry narrowing problem was therefore not sufficient to explain the whole mismatch. The natural body still did not create the target's `r9/r8` mask lifetime or the target's later `r2/r1/r3/r4` choreography.

### 6. Natural body with a wide `s32` offset parameter/local

Source shape: `s32 offsetInput`, explicit `(s16)` assignment to a local, natural RGB555 expressions and clamps. Several destination-pointer forms were tested (`volatile` and non-volatile).

The pointer qualifier did not solve the mismatch. The first mismatch in the best of these runs was one of:

```text

current 0x00000018: mov r3, #248
```

or, when the mask setup was not emitted at that location:

```text
target 0x00000018: mov r1, #248
current 0x00000018: <no instruction>
```

The difference was not the RGB555 semantics; it was the compiler's choice of live registers for the invariant masks and offset.

### 7. Raw-channel staging variants

Source shape: load `color`, keep `greenRaw = color & 0x3E0` and `blueRaw = color & 0x7C00`, then shift/add the staged values, with different assignment orders for red/green/blue.

The first mismatch was still at mask setup in the normal-pressure versions:

```text
target 0x00000018: mov r1, #248
current 0x00000018: mov r0, #248
```

Adding enough long-lived raw temporaries increased register pressure and could move the first mismatch all the way into the prologue, for example:

```text
target 0x00000002: mov r7, r9
current 0x00000002: mov r7, r10
```

or:

```text
target 0x00000002: mov r7, r9
current 0x00000002: mov r7, r8
```

Those variants were rejected because they changed the callee-saved register choreography before the function body.

### 8. Channel assignment and declaration-order permutations

Reordering red/green/blue assignments, changing declaration order, and moving the red temporary between `temp_r2`, `temp_r2_2`, and `var_r1` changed later channel allocation but did not reproduce the target. The recurring first mismatch was:

```text
target 0x00000018: mov r1, #248
current 0x00000018: mov r0, #248
```

or the same target instruction versus `mov r3, #248`. One permutation that reused `temp_r2` for red instead of a separate red local changed the prologue allocation first:

```text
target 0x00000002: mov r7, r9
current 0x00000002: mov r7, r8
```

The target's eventual channel destinations (`r1`, `r3`, `r4`) were not obtained by assignment order alone; they depend on the complete live-range shape, including the two high-register mask values.

## What to try next

1. Start from the natural RGB555 body, but model the ABI-level third argument as a wide `s32` value narrowed once into a signed local before the first loop. The target proves the signed narrowing operation, while the direct `s16` prototype suppresses it.
2. Keep the bank as `u8` and use the simple `BG_PLTT + (bank << 9)` expression only as a semantic baseline. Then test equivalent source forms that preserve the target's address calculation without introducing extra long-lived temporaries.
3. Use `uv run tools/asm-annotated.py src/system.c sub_8057A7C --all-passes` after each small source change. Focus on the `.lreg`/`.greg` assignments around the mask setup and the first `ldrh`, rather than changing all channel declarations at once.
4. Search for the exact source expression that makes agbcc hoist `0x3E0` into `r9` and `0x7C00` into `r8` while retaining the color in `r2`. The target likely used two loop-invariant locals or an expression/lifetime arrangement not yet reproduced; this is an inference, not established fact.
5. Once the entry and first `ldrh` sequence match, tune the channel expression order and clamp temporaries to obtain `r1/r3/r4`. Do not use inline assembly or register pinning; the existing attempts show that compiler-output-shaped casts can fix one opcode while worsening the source shape and the remaining register allocation.

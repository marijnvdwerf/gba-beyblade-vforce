# event.c — initEventListeners (0x080540EC), 2026-09-13

Matched. 288 B, hosted in `src/event.c`. Signature `void initEventListeners(unk32 levelId)`
(header already declared it that way; both call sites in `src/gameinit.c` pass an `unk32`
local, and the prologue `lsl #16 / lsr #16` is the CSE'd truncation for the `u16`
parameters of `loadLevelGeometry` / `getLevelMetadata`, not the parameter's own
normalization).

## Layout / type facts

- Frame is `add sp, sp, #0xfffffee4` = 0x11C = exactly `sizeof(LevelGeometryAddresses)`,
  followed by a *second*, later `add sp, sp, #0xffffff80` and `mov r9, sp` / `mov sp, r9`
  in the epilogue. That second adjustment plus the saved sp is the GNU VLA signature.
  Contrast the matched sibling `initLevelEnvironmentActors` (envactor.c), which uses fixed
  `[0x20]` arrays: one `add sp, sp, r4` and no sp save. So `unk32 listenerIds[maxListeners];`
  with a non-const `s32 maxListeners = 0x20;` is required; the byte count folds to 0x80
  inside the same basic block while the in-loop `cmp`/`printf` uses keep `maxListeners`
  in a register.
- `const s32 maxListeners` is wrong: with `const`, agbcc folds the compare and the printf
  argument to immediates and allocno 32 disappears entirely.
- `listenerCount` and `maxListeners` are both signed: `0x90 cmp sl, r6` + `0x92 ble`.
  (The entry guard's `bge` proves nothing about `listenerCount` — that compare is
  `i < lineCount` with `i`'s zero CSE'd onto `listenerCount`'s register; it is evidence
  about `i`, see below.)
- `i` is signed (`s32`), proven by codegen at two sites: the loop back-edge test
  `0xA2 cmp r4, r0` / `0xA4 blt 0x70`, and its duplicated entry copy `0x6A cmp r10, r0`
  / `0x6C bge 0xA6`. `lineCount` is `s32` (`LevelGeometryTable.lineCount`, +8), so if `i`
  were `unk32` the usual arithmetic conversions would make `i < lineCount` unsigned.
  Measured: declaring `unk32 i` changes exactly two rows and nothing else —
  `0x6C bge -> bhs` and `0xA4 blt -> blo` — and fails `compare`. Nothing else in the
  function carries signedness information about `i` (`listenerIds[]` is `unk32`,
  `GetLineMetaData`'s second parameter is `unk32`), so this compare pair is the sole
  citation.
- `AllocatedBlock.address` at +0, `LevelGeometryTable.lineCount` at +8 (`s32`, `blt`).
- No struct/header changes were needed.

## Byte-required temporaries

- `void* buffer = block->address;` — byte-required. Without it the target's single
  `ldr r4, [r6]` (value kept live across `_call_via_r3` and reused for the
  `_gameData->unkCA4` store) becomes two loads, and the `_gameData` address/offset
  materialization at the tail changes (`add r2, #4` reuse is lost).
- `bytes` kept (3 uses); `lineMetadata` kept (2 uses).
- Block-scoped vs function-scoped declarations of `lineMetadata` / `block` / `bytes`:
  byte-identical. Function scope kept.
- `for (i = 0; ...)` vs `i = 0; if (listenerCount < lineCount) { do ... while }`
  (the envactor idiom): byte-identical. The plain `for` was kept.

## The store must be an indexed store, not a cursor

`listenerIds[listenerCount++] = i;` — NOT `*listenerPtr++ = i;` with a cursor local.
Both emit `stmia r5!, {r4}`, but they differ in where the cursor is initialised:

- explicit cursor local → `mov r5, sp` emitted *before* the duplicated loop-entry test;
- indexed store → loop strength reduction creates the giv, so its initial value lands in
  the loop *preheader*, i.e. *after* `cmp sl, r0 / bge` — which is what the target has.
  (The `str` + `add #4` pair is then merged into the post-increment `stmia` by flow.c.)

## The register-role swap (count in `sl` vs `r6`) — root cause

First stable divergence at 0x26: target `mov r0,#0; mov sl,r0; mov r6,#0x20`, candidate
`mov r6,#0; mov r0,#0x20; mov sl,r0`. Everything downstream (`mov r2, sl` before each
`_gameData` store, `mov r2,#202; lsl #4` instead of `sub r2,#4`, `mov r2,#1; add sl,r2`
instead of `add r6,#1`, `mov r0,sl; cmp r0,#0`) is a consequence of the counter living in
a high register.

agbcc's `global.c` orders allocnos by

    pri = floor_log2(n_refs) * n_refs / live_length * 10000

This was verified against the `.greg` "Registers to be allocated in sorted order" list for
all 12 global allocnos of this function. With the `if (a && b) { ... }` nesting:

    31 (listenerCount) refs=14 ll=182 -> 2307
    32 (maxListeners)  refs= 5 ll=114 ->  877

so `listenerCount` is always allocated first and always takes the best free low
callee-saved register (`r4`/`r5` go to `i` and `block`, `r7` is the frame pointer because
of the VLA, so it takes `r6`), leaving `maxListeners` in `sl`. No amount of scope,
declaration-order, loop-shape, signedness, `sizeof` vs `* 4`, fused-increment or
VLA-bound-spelling churn moves those two numbers — all were measured and left
refs/live_length for 31 and 32 bit-identical. A diagnostic probe that added two extra
in-loop references to `maxListeners` only raised it to refs=7/ll=122 (still below), and
the cliff needed is refs>=9.

**What actually flipped it: early returns instead of the nested `if`.**

    _gameData->unkCA8 = 0;
    if (metadata == NULL) { return; }
    if (geometryData == NULL) { return; }
    getLevelGeometryAddresses(...);

replacing

    if (metadata != NULL && geometryData != NULL) { ... }

This is the idiom of the already-matched sibling `initLevelEnvironmentActors`. It splits
the entry region into separate basic blocks with their own `NOTE_INSN_BLOCK` scopes; the
resulting allocno set drops from 12 to 11 (the `bytes` temp/user-var pair collapses), the
sorted order becomes `46 45 49 47 31 23 27 105 32 44 103`, and `maxListeners` ends up in
`r6` with `listenerCount` in `sl` — matching the target exactly, every instruction.

Lesson: when a two-variable register-role swap looks arithmetically unreachable from the
allocator's priority formula, the lever is not the two variables — it is the *basic-block
structure around them*. Check how a matched sibling in the same family spells its guards
before concluding the swap is unreachable.

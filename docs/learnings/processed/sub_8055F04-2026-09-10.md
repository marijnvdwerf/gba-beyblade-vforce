# sub_8055F04 (0x08055F04, src/collision.c) — 2026-09-10

Matched. 40 bytes, hosted in `src/collision.c` between `sub_8055D64` and the
`8055f2c` dump.

## The problem

Everything except one instruction matched with a two-call body
(`sub_804E358(angle, rider->unk10 >> 4); sub_804E154(rider, 0, 0);`).
The target has a dead shift right after the first call:

```
	bl	sub_804E358
	lsl	r0, r0, #0x10      @ result immediately overwritten by the next insn
	add	r0, r4, #0
```

## What produces it

The body is the first three statements of the sibling `sub_8055D64`, with the
result unused:

```c
    angleDelta = sub_804E358(angle, rider->unk10 >> 4);   /* s16 */
    if (angleDelta < 0)
        angleDelta = -angleDelta;
    angleThreshold = angleDelta * 0x10000;                /* s32, never read */
```

`angleDelta * 0x10000` on the `s16` call result is a single `lsl #16` (combine
folds the sign-extension into the shift: the high bits do not survive it). It
survives dead-code elimination only when the value was still live at agbcc's
`flow` pass; the `if (angleDelta < 0) angleDelta = -angleDelta;` is what keeps
it live long enough, and the rest of the chain (compare, branch, `neg`) is
deleted afterwards.

Both statements are byte-required: neither the negation nor the multiply can be
dropped, and neither works without the other.

## Method note

Probing was done by compiling a scratch TU with candidate bodies directly
through `tools/agbcc` (same flags as the build: `-mthumb-interwork -O2
-fhex-asm`), so eight variants cost one compile instead of eight ROM builds.
Two ROM builds total were needed (baseline + final).

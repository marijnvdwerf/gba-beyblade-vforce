## agent-aee513f785706f4b3 — src/gameinit.c — initGame

### Diagnosis

The overlay-struct approach (`GameDataC24`, `GameDataC28`, etc.) is a code smell the style rules explicitly forbid — it is raw offset arithmetic dressed up as struct access. The original programmer had a single `GameData` struct with named fields at each offset and simply wrote `_gameData->unkC24 |= 0xFFFF`. The scoped blocks with intermediate cast pointers add artificial temporaries that will generate extra loads and register pressure. The `(unk32)_gameData` intermediate cast is particularly suspicious — it forces the pointer through an integer, which is exactly the kind of offset-arithmetic workaround the rules ban.

### Proposed natural C

```c
void initGame(void)
{
    AllocatedBlock* block;

    block = slowAllocate(0x1644);
    _levelDataBlockPtr = block;
    _gameData = (GameData*)block->address;
    __fastMemoryClearARM(0, (u8*)_gameData + 0x1620, 0x18);

    _gameData->unkC2C = -1;

    _gameData->unkB56 = 0;
    _gameData->unkB34 = 0;

    _gameData->unk1640 = 0;
    _gameData->unkB58 = 0;
    sub_8053F0C(1);

```

Notes on the `__fastMemoryClearARM` call: the target computes `r1 = _gameData + 0x1620` as the destination. The cleanest source is `(u8*)_gameData + 0x1620` — this is a byte-offset computation to a specific sub-region. If the function's prototype expects `void*`, the cast is implicit. The `0x1620` arithmetic is acceptable here because it is an argument to a memset-like call, not a dereference through a typed pointer.

The `|= 0xFFFF` on `unkC24` and `unkC26` looks odd but exactly reproduces the target's `ldrh; orr r0, r5; strh` pattern — it is a halfword read-modify-write that sets all 16 bits. The struct fields `unkC24` and `unkC26` are `s16` (per the existing `GameData` definition, which already has them).

The `zero` variable from the agent's version is unnecessary. The target does `mov r2, #0` once at 0x805336A and reuses `r2` for all zero stores — but this is register reuse by the compiler, not a source-level shared variable. Writing `= 0` at each site is the natural source; agbcc will CSE the zero.

If the `_gameData` reload pattern causes register issues: the target reloads `_gameData` (via `ldr r1, [r4]` or `ldr r0, [r4]`) between groups of stores. This happens naturally when the compiler cannot prove the pointer is unchanged across calls. The `__fastMemoryClearARM` call clobbers caller-saved registers, forcing a reload afterward. Subsequent stores may be grouped without reloads if the compiler keeps `r1` live.

## agent-a7d4f3a332d49ca2f — src/system.c — sub_8057A7C

### Diagnosis

The agent's C is almost verbatim from the raw-decomp (which itself was a mechanical m2c output). The problems are: (1) overly explicit shift/cast choreography that the original programmer would not have written — e.g. `(s32)(s16)temp_r2_2 > 0x1F` and `(((s32)(s16)var_r1) << 0x10) < 0` are compiler-output shapes; (2) the parameter types are wrong — the target does `lsl r1, r1, #0x18; lsr r1, r1, #0xf` which is a `u8` argument being shifted to compute a palette address, and `lsl r2, r2, #0x10; asr r5, r2, #0x10` which is sign-extending a `s16` argument; (3) the final combine expression is transcribed shift-for-shift rather than being written as RGB555 channel recombination.

This function adjusts palette brightness: it takes an 8-color palette source, a palette index, and a brightness offset, then clamps each RGB555 channel to [0, 31] and writes the result.

### Proposed natural C

```c
void sub_8057A7C(u16* src, u8 paletteIndex, s16 offset)
{
    vu16* dst;
    u16 color;
    s16 r;
    s16 g;
    s16 b;
    u16 i;

    dst = (vu16*)(BG_PLTT + (paletteIndex << 9));
    i = 0;
    do {
        color = *src;
        r = (color & 0x1F) + offset;
        g = ((color & 0x3E0) >> 5) + offset;
        b = ((color & 0x7C00) >> 10) + offset;
        if (r > 31) {
            r = 31;
        }
        if (g > 31) {
            g = 31;
        }
        if (b > 31) {
            b = 31;
        }
        if (r < 0) {
            r = 0;
        }
        if (g < 0) {
            g = 0;
        }
        if (b < 0) {
            b = 0;
        }
        *dst = r | (g << 5) | (b << 10);
        src++;
        dst++;
        i = (u16)(i + 1);
    } while (i <= 7);
}
```

If the signed clamp comparisons generate wrong branch opcodes, the channels may need to stay `u16` with explicit sign-extension casts at the comparison points. But try `s16` first — the target's clamp sequence is `lsl #16; asr #16; cmp #0x1f; ble` (signed extend then signed compare) for the > 31 test, and `lsl #16; cmp #0; bge` for the < 0 test. With `s16` locals, agbcc should produce the sign-extension and signed compare naturally.

### Asm evidence

- **arg1 is `u8`**: `lsl r1, r1, #0x18; lsr r1, r1, #0xf` = zero-extend byte then shift left 9. The `u8` parameter type produces `lsl #24; lsr #24` ABI narrowing, and the `<< 9` comes from `paletteIndex << 9`. But the target combines both into `lsl #0x18; lsr #0xf` (= `lsr #(24-9)` = shift right 15 after the zero-extend, net effect: `(u32)(u8)arg1 << 9`). To get this merged shift, the source should spell it as `paletteIndex << 9` with `u8 paletteIndex` — agbcc will merge the ABI narrowing with the shift.
- **arg2 is `s16`**: `lsl r2, r2, #0x10; asr r5, r2, #0x10` = sign-extend halfword. The `asr` proves signed.
- **Channel mask constants in callee-saved regs**: `0x3E0` in `r9` and `0x7C00` in `r8`. These are `mov #0xf8; lsl #2` (= 0x3E0) and `mov #0xf8; lsl #7` (= 0x7C00). The compiler hoists loop-invariant mask constants into callee-saved registers.
- **Clamp > 31**: `lsl r2, r2, #0x10; lsr rN, r2, #0x10` (u16 truncation) followed by `asr r2, r2, #0x10; cmp r2, #0x1f; ble` — the compiler sign-extends the u16-truncated value to test the signed comparison. With `s16` locals the sign-extension is implicit.
- **Clamp < 0**: `lsl r0, rN, #0x10; cmp r0, #0; bge` — tests if the left-shifted value is negative (sign bit of the s16 in bit 31). This is `(s16)val < 0`.
- **Final combine**: `lsl r0, r3, #0x10; asr r0, r0, #0xb` = `(s16)g << 5`; `lsl r0, r4, #0x10; asr r0, r0, #0x6` = `(s16)b << 10`. The shifts go through sign-extension — this might require `(s16)g << 5` in source or just `g << 5` if the compiler sign-extends before shifting anyway.
- **Loop counter**: `u16 i` — the target does `lsl r0, r0, #0x10; lsr r0, r0, #0x10` (u16 truncation) on the increment, then `cmp r0, #7; bls` (unsigned <=). A `u16` counter with `<= 7` or `i <= 7U` test reproduces this.
- **`vu16*` dst**: the stores to palette MMIO should be volatile to prevent reordering/elision. The `strh r1, [r6]` write to the palette address confirms direct MMIO write.
